# FSEP-0003: Fastlet Control Authentication

## Problem and goals

The Fastlet control API is a plain HTTP+JSON protocol served on the Pod IP at port 5758 (`internal/fastlet/server/rpc_server.go`, `internal/protocol/fastlet/fastlet_client.go`). It carries the highest-authority operations in the system — atomic Create, Delete, snapshot, drain, handler relay, and a heartbeat that reports the full local Sandbox inventory — and it performs no application-layer authentication: the server installs no auth middleware on its mux, and the client sends no credential, only trace headers. The only isolation is a NetworkPolicy that restricts port 5758 to Pods carrying the platform control-plane labels (`config/network-policy/default.yaml`). That is a network-location trust model: the identity of a caller is the network position it happens to hold.

Three gaps follow from that model. First, the policy only holds where the CNI enforces NetworkPolicy and where label selectors can be trusted; a compromised Pod in the system namespace, a forged label, or a cluster whose plugin ignores policies exposes the full lifecycle API. Second, the connection is unauthenticated and unencrypted, so nothing on the path binds a request to an identity at all. Third, the protection is asymmetric with the data plane, which already verifies per-route Ed25519 credentials fencing namespace, Sandbox UID, port, and Fastlet Pod UID (`internal/dataplane/auth/credential.go`, `internal/dataplane/fastletproxy/proxy.go`): the lower-authority plane is better defended than the higher-authority one.

This proposal makes authentication on the Fastlet control API **always enabled** with no disable switch, under these goals:

- Every control endpoint except `/livez`, `/readyz`, `/metrics`, and `/api/v2/fastlet/heartbeat` rejects callers that do not present a valid, audience-bound token issued to an allow-listed ServiceAccount. Heartbeat stays open deliberately: diagnostics tooling and the heartbeat loop rely on it and it grants no intent-changing authority.
- No operator-managed key material. Every credential in the design — the control-plane caller tokens and the Fastlet's key-fetch token alike — is a short-lived Kubernetes ServiceAccount token minted through the TokenRequest API (directly, or through the kubelet's projected-token machinery) and rotated by lifetime, in the manner Kubernetes components authenticate to each other; Kubernetes signs, bounds, and revokes them.
- Low steady-state overhead. No per-request network round trip and no public-key operation on the hot path: verification results are cached per token.
- Compatibility with the existing Fastlet security posture: Fastlet Pods keep `automountServiceAccountToken` forced off (`docs/reference/configuration.md`) and hold exactly one Kubernetes credential — a projected token for a dedicated, discovery-only `fast-sandbox-fastlet` ServiceAccount, mounted as an explicit volume into the Fastlet container alone so the proxy sidecar and any template sidecars never see it.
- Fail-closed behavior everywhere: a cluster whose RBAC has not been updated, a Fastlet without its issuer anchor, a Fastlet without its key-fetch token, or an unreachable issuer degrades into loud errors, never into silent unauthenticated traffic.

### Non-goals

- Transport encryption (mTLS or TLS on port 5758). Caller identity is established at the application layer; wire encryption is a separate decision that can be layered later without protocol change.
- The data plane. Sandbox Proxy traffic is already credential-gated (`docs/concepts/architecture.md`), and this proposal does not alter it.
- Migrating the Fastlet control protocol to gRPC. The protocol stays HTTP+JSON; performance is not the bottleneck (runtime startup dominates Create latency) and the curl/kubectl diagnostics surface depends on plain HTTP.
- Protecting user protocols (Execd and friends). Fast Sandbox does not define them.
- A mixed-version or downgrade-tolerant wire protocol. This is an accepted breaking change; see Compatibility.

## Proposal and tradeoffs

The client half lives in the control plane; the server half lives in the Fastlet; a new `internal/fastletauth` package holds both halves plus the HTTP middleware.

**Client: TokenRequest-issued ServiceAccount tokens.** `fastletauth.TokenRequestSource` mints a token for the Pod's own ServiceAccount through the TokenRequest API with audience `fast-sandbox-fastlet` (`fastletauth.Audience`) and an expiration of one hour, caches it, and re-mints when the remaining lifetime drops below twenty minutes, using the `ExpirationTimestamp` the API server returns. The identity (namespace and ServiceAccount name) is derived from the Pod's own projected token and namespace file, with `FASTLET_AUTH_NAMESPACE` / `FASTLET_AUTH_SERVICE_ACCOUNT` env overrides for processes running outside a Pod. `FastletClient.SetTokenSource` installs the source; every request, heartbeat included, carries `Authorization: Bearer <token>`, and a token-acquisition failure fails the call closed — no request ever leaves without a credential.

**Server: local JWT verification against the issuer's published keys.** `fastletauth.Authenticator` validates tokens the same way the API server validates ServiceAccount tokens: it fetches the issuer's OIDC discovery document and JWKS once, caches the signing keys (RS256 and ES256 P-256), and verifies signature, `exp`, `nbf`, `iss`, `aud`, and `sub` locally. Unknown `kid` values trigger a JWKS refresh throttled to one attempt per thirty seconds, so API-server signing-key rotation is followed without restarts and a forged-kid flood cannot become a request storm. Positive verdicts are cached for one minute and negative verdicts for five seconds, which reduces the per-request cost to a SHA-256 and a map lookup and keeps the amortized public-key work near zero. The subject must be an exact `system:serviceaccount:<namespace>:<name>` entry in the allow list, which defaults to the platform `fast-sandbox-fastpath` and `fast-sandbox-controller` ServiceAccounts.

**The allow list travels through the platform like the anchor.** Installations whose control plane does not run in `fast-sandbox-system` would otherwise have to patch every Pool template, and a missed Pool would 403 its control plane. The controller binary therefore takes `--fastlet-auth-subjects` (environment fallback `FASTLET_AUTH_SUBJECTS`), a comma-separated subject list that the Pool Controller injects into every Fastlet Pod as `FASTLET_AUTH_ALLOWED_SUBJECTS` through the same platform-owned env path as the anchor; an unset flag applies the built-in platform default, so standard installs stay zero-configuration. The three authentication env variables are runtime-owned: the Pool Controller strips them from Pool templates before injection, so a Pool template can neither weaken the allow list nor redirect the issuer anchor.

**Issuer key access is authenticated, not anonymous.** The Fastlet fetches the discovery document and JWKS with a credential. The Pool Controller provisions a dedicated `fast-sandbox-fastlet` ServiceAccount in every Pool namespace, forces it into the Pod spec, and mounts its projected token — an explicit `serviceAccountToken` projection with a one-hour expiration, at the conventional `/var/run/secrets/kubernetes.io/serviceaccount` mount path — as a platform-owned volume into the Fastlet container alone, so the proxy sidecar and any template sidecars never receive it (`automountServiceAccountToken` stays off; that flag does not disable explicit projected volumes). The fetch re-reads the token file on every request, so kubelet's standard rotation — refresh at 80% of the TTL — is followed without restarts, and the fetch never needs a Kubernetes client beyond the plain HTTPS request it already makes. Authorization costs nothing on a default cluster: the built-in `system:service-account-issuer-discovery` ClusterRole is bound by default to the `system:serviceaccounts` group, so any ServiceAccount token — including this one — can read the two public-key endpoints. Because some operators strip bootstrap bindings on hardened clusters, the deployment's RBAC (`config/rbac/base.yaml`, mirrored by the OpenSandbox base chart) ships a self-contained authenticated equivalent: a ClusterRole granting GET on `/.well-known/openid-configuration` and `/openid/v1/jwks` — the exact non-resource URLs of the built-in role — bound through a ClusterRoleBinding to the `system:serviceaccounts` group, the same subjects Kubernetes binds by default. No rule ever binds to `system:unauthenticated`; anonymous reads of the issuer keys, which earlier revisions of this proposal required and which Alibaba Cloud ACK marketplace admission (`anonymousUserRBACBinding`) rejects outright, are gone.

**The client preserves rejection semantics.** The Fastlet middleware answers rejected and unavailable requests with a machine-readable error envelope carrying the HTTP status, and `FastletClient` reads the body before classifying the response, so a plain-text or envelope error never degrades into a decode failure that hides the status. Authentication outcomes are a distinct class from runtime outcomes: an auth rejection or auth-unavailability provably never reached admission, so the client maps them to errors that are separate from the create protocol's `UnknownOutcome` disposition — retries of an auth-rejected Create are always safe and reconciliation is never triggered for a call that did not happen.

**The anchor travels with the Pod template.** The Fastlet's discovery-only credential authenticates it to the API server but tells it nothing about which issuer to trust, so the Pool Controller resolves the anchor from its own projected ServiceAccount identity at startup — issuer URL plus base64 cluster CA bundle (`fastletauth.ResolveIssuerAnchor`) — and injects `FASTLET_AUTH_ISSUER` and `FASTLET_AUTH_CA_BUNDLE` as platform-owned env into every Fastlet Pod it materializes. The injection is part of the Pod template hash, as is the token mount, so both participate in the normal Pool rolling update. The issuer URL is the trust anchor and never comes from an incoming token, so an attacker cannot redirect key material to a host they control.

**Enforcement mapping.** `fastletauth.Middleware` wraps the server mux: exempt paths pass through; a missing or invalid token yields 401 with `WWW-Authenticate`; a valid token from a non-allow-listed subject yields 403; a validator failure (issuer unreachable) yields 503 so callers retry instead of treating the call as rejected. The authenticated subject is attached to the request context.

**Considered alternatives.**

- *TokenReview validation* (the literal webhook pattern) was rejected: it couples every cold verdict to an API-server round trip, requires `tokenreviews/create` RBAC bound to the deployer-controlled Fastlet ServiceAccount (or a cluster-scope `system:auth-delegator` binding provisioned by the Pool Controller), and pulls client-go into the deliberately node-local Fastlet binary. Local JWKS verification has the same trust root with none of that, and it is what the API server itself does with ServiceAccount tokens.
- *Operator-provisioned shared keys* (the route-keys Secret pattern) were rejected because the credential would be long-lived and hand-distributed, which is exactly what this proposal removes.
- *Keeping the anonymous issuer binding* was rejected: it hard-fails marketplace admission checks that forbid any binding to `system:unauthenticated`, widens the two endpoints to every unauthenticated caller in the cluster, and earlier revisions shipped the binding even in installations with the runtime disabled.
- *Control-plane-provisioned static key-fetch tokens* (a TokenRequest result injected as env at Pod creation) were rejected: the token outlives neither its one-hour TTL nor the Pod, and re-minting it requires exactly the Kubernetes API access this design keeps off the Fastlet; the kubelet-projected volume provides the same bound, auto-rotating credential without any Fastlet-side Kubernetes client.
- *Ephemeral per-replica signing keys distributed at Pod creation* were rejected: Fastlet Pods cannot track a key set that changes on every control-plane restart, so rolling updates would brownout the control path.
- *mTLS* was rejected for this scope: certificate distribution is operator configuration, and by itself it answers "which Pod spoke TLS" without answering "is this ServiceAccount allowed to mutate Sandboxes".

**Risks.** A managed cluster whose `--service-account-issuer` URL is not reachable from Pods fails verification with 503s; the standard in-cluster issuer (`kubernetes.default.svc`) is reachable and is the documented default. A deleted ServiceAccount's already-minted tokens stay valid until expiry — bounded by the one-hour TTL, the same window a cached TokenReview verdict would have. The Fastlet's mounted token is discovery-only by construction: outside the two public-key endpoints it carries no resource permissions, and its default API-server audience does not match `fastletauth.Audience`, so presenting it to a Fastlet control API fails verification; a compromise of the token is bounded by the same one-hour rotation window as a control-plane token. Both original risks are recorded as accepted limitations rather than open questions.

## Identity and RBAC map

Every identity ships in `config/rbac/base.yaml`, mirrored by the OpenSandbox base chart; each ClusterRole is bound to exactly one identity, and the only group subject in the file is the discovery pair's `system:serviceaccounts`. This section is the authoritative statement of which component holds which grants and what consumes them. The control-authentication grants — per-identity token minting and issuer discovery — are this proposal's subject; narrowing the remaining cluster-scoped reach (Secret, Node, and cross-namespace workload verbs) to managed namespaces is the admission-hardening effort's separate track.

- **`fast-sandbox-controller`** (`fast-sandbox-system`; control-plane reconciler). Cluster-scoped by necessity: the Sandbox CRDs are cluster-scoped and Fastlet Pods are materialized in every Pool namespace. Per resource, with its consumer: `pods` full CRUD — materializes, replaces, and drains Fastlet Pods; `configmaps` and `secrets` full CRUD — compiled registry Secrets, infra/runtime/settings plan ConfigMaps in Pool namespaces, registry pull credentials, and template build inputs; `serviceaccounts` get/create and `roles`/`rolebindings` get/list/watch/create/update — provisions the builder identity in each template namespace and the `fast-sandbox-fastlet` identity in each Pool namespace, converging pre-existing same-named objects onto the enforced shape; `events` create/patch/update; `runtimeclasses` get/list/watch; the four Sandbox CRD kinds and their statuses full CRUD; `leases` full for leader election. `nodes` get/list/watch plus write verbs are also present in the role, but the reconciler's code paths today consume node identity only through Fastlet-reported inventory — the write verbs' consumer audit belongs to the admission-hardening track, not this proposal.
- **`fast-sandbox-fastpath`** (`fast-sandbox-system`; the control-plane caller of the Fastlet control API). ClusterRole, read-mostly: `pods` and `sandboxpools` get/list/watch, `sandboxes` and `sandboxsnapshots` with their statuses full CRUD. Plus the namespaced token-minter Role below. It never fetches issuer keys, so it holds no discovery grant.
- **`fast-sandbox-fastpath-token-minter` and `fast-sandbox-controller-token-minter`** (Roles in `fast-sandbox-system`, one RoleBinding each). Each grants `create` on `serviceaccounts/token` with `resourceNames` fencing to exactly the ServiceAccount its RoleBinding binds. `serviceaccounts/token` RBAC is evaluated in the target ServiceAccount's namespace and `resourceNames` matches the bare name, so a cluster-scoped rule would have allowed minting tokens for same-named ServiceAccounts in tenant namespaces — a lateral-movement primitive for a compromised control plane that the namespaced scope removes — and `fast-sandbox-fastpath` cannot mint controller tokens and thereby inherit their broader permissions. These two Roles, their RoleBindings, and the discovery pair below are everything this design adds to stock Kubernetes RBAC.
- **`fast-sandbox-fastlet`** (NEW; one per Pool namespace, provisioned by the Pool Controller before the first Fastlet Pod referencing it). No namespaced RBAC at all; its only cluster-visible authority is GET on the two issuer public-key non-resource URLs, restating what Kubernetes binds by default so hardened clusters that stripped the bootstrap bindings still admit key fetches:

  ```yaml
  apiVersion: rbac.authorization.k8s.io/v1
  kind: ClusterRole
  metadata:
    name: fast-sandbox-fastlet-issuer-discovery
  rules:
  - verbs: ["get"]
    nonResourceURLs: ["/.well-known/openid-configuration", "/openid/v1/jwks"]
  ---
  apiVersion: rbac.authorization.k8s.io/v1
  kind: ClusterRoleBinding
  metadata:
    name: fast-sandbox-fastlet-issuer-discovery
  roleRef: {apiGroup: rbac.authorization.k8s.io, kind: ClusterRole, name: fast-sandbox-fastlet-issuer-discovery}
  subjects:
  - {kind: Group, name: system:serviceaccounts, apiGroup: rbac.authorization.k8s.io}
  ```

  Nothing binds to `system:unauthenticated`. Explicit negative space: no resource-API verbs of any kind, no `tokenreviews`, no TokenRequest minting (the control plane mints; the Fastlet only presents), and no watch caches — the fetch stays a plain HTTPS request.
- **`fast-sandbox-sandboxtemplate-builder`** (per template namespace, provisioned on demand by the SandboxTemplate controller). The build Pod runs in the template's (tenant) namespace, owned by the template for cascading deletion; the identity holds a namespaced Role granting `pods/patch` only, for the builder to self-report its outcome. Outside this proposal's authentication path.
- **`fast-sandbox-proxy`** (`fast-sandbox-system` Deployment; the client-visible Sandbox Proxy). ClusterRole, read-only: `pods` and `sandboxes` get/list/watch as its routing source. Data-plane traffic keeps its own credential fencing; this proposal does not alter it.
- **`fast-sandbox-janitor`** (`fast-sandbox-system` DaemonSet; node janitor). ClusterRole, read-only: `pods` and `sandboxes` get/list/watch. Outside this proposal's authentication path.

## Compatibility

This is an accepted breaking change at the wire level; there is no opt-out and no protocol negotiation.

- **Supported combinations.** Control-plane components and Fastlets must both be this version or newer. New control plane against an old Fastlet works: the old server ignores the `Authorization` header, and the interim state is the previous (unauthenticated) behavior, not an outage. Old control plane against a new Fastlet fails closed with 401 on every lifecycle call: loud, and safe in the security direction.
- **Upgrade order.** Apply the updated RBAC first, then roll the control plane (Fast-Path and controller Deployments), then let the Pool Controller roll Fastlet Pods. This order never crosses a broken combination.
- **Rollback order.** Fastlets back first, then the control plane. The reverse order crosses old-control-plane + new-Fastlet and 401s the control path until both sides are back.
- **RBAC.** The complete identity-to-grant map is specified in the Identity and RBAC map section and ships in `config/rbac/base.yaml`, mirrored by the OpenSandbox base chart in lockstep (`manifests/charts/base/templates/fast-sandbox-rbac.yaml`); keep the two in sync when changing either. The dedicated `fast-sandbox-fastlet` ServiceAccount in each Pool namespace is provisioned by the Pool Controller before the first Fastlet Pod referencing it, following the on-demand pattern the template builder ServiceAccount already uses. A cluster without the token-minting grant fails at the first Fastlet call with the underlying Forbidden error visible in the wrapped message; a cluster missing the discovery binding fails the same way on the first key fetch.
- **Configuration surface.** No CRD, gRPC API, SDK, or CLI changes. New environment variables are platform-owned (`FASTLET_AUTH_ISSUER`, `FASTLET_AUTH_CA_BUNDLE`, `FASTLET_AUTH_ALLOWED_SUBJECTS`) or deployment-tunable overrides (`--fastlet-auth-subjects` with the `FASTLET_AUTH_SUBJECTS` env fallback on the control plane, `FASTLET_AUTH_AUDIENCE`, `FASTLET_AUTH_NAMESPACE`, `FASTLET_AUTH_SERVICE_ACCOUNT`, `FASTLET_AUTH_KEYFETCH_TOKEN` for host-process Fastlet runs), documented in `docs/reference/configuration.md`. The three platform-owned authentication variables are stripped from Pool templates before injection, so a Pool template cannot relax the allow list or redirect the issuer anchor; the key-fetch credential is equally platform-owned — the Pool Controller strips template-supplied `serviceAccountName`, `automountServiceAccountToken`, and any template volume or mount colliding with the auth-token volume before forcing the dedicated ServiceAccount and its projected volume, so a Pool template cannot swap the fetching identity, and the override env is stripped and re-injected empty alongside the other auth keys so an `envFrom` reference cannot supply it either. The injected anchor, allow list, and token mount change the Fastlet Pod template hash, so upgrading rolls every Fastlet Pool; live Sandboxes on those Pods end according to the platform's standard Fastlet Pod replacement semantics, exactly as with any Fastlet version bump.
- **Kubernetes version floor.** The design uses three mechanisms that settled at Kubernetes v1.22: the GA TokenRequest API (`authentication.k8s.io/v1` with the `serviceaccounts/token` subresource, audience scoping, and `expirationSeconds`), bound projected ServiceAccount tokens (the control plane reads its own projected token to anchor the issuer), and the API server's OIDC discovery and JWKS endpoints. RBAC `resourceNames` predates that floor. No feature gates or non-default admission plugins are required, and the verifier accepts both RSA (RS256) and EC P-256 (ES256) ServiceAccount signing keys, so clusters using either key type work unchanged. The practical floor is v1.24: legacy never-expiring ServiceAccount tokens were removed there, which is the token shape this design assumes; v1.20 and v1.21 only expose a beta TokenRequest that current client-go no longer speaks. The repository's own integration and performance environments run v1.27+, and current managed distributions (ACK/GKE/EKS) ship v1.24 or newer by default.
- **Local development.** A host-process controller can still authenticate by exporting `FASTLET_AUTH_NAMESPACE`, `FASTLET_AUTH_SERVICE_ACCOUNT`, and an identity whose RBAC allows minting its own tokens; without them the controller exits at startup with a directed error. There is no unauthenticated mode to fall back to.

## Test plan

Unit tests cover the real verification paths against a local OIDC issuer harness (`internal/fastletauth/fastletauthtest`) that serves discovery and JWKS and mints signed tokens:

- Acceptance of RS256 and ES256 P-256 tokens; rejection of empty, malformed, and over-segmented tokens, wrong audience, wrong issuer, expired and not-yet-valid tokens, bad signatures, unknown `kid`, unsupported algorithms, and payloads without `exp`.
- Allow-list enforcement (403 class) and verdict caching: a cached positive verdict survives an allow-list change until the TTL elapses; unknown-`kid` refreshes are throttled; key rotation is followed after publication.
- `TokenRequestSource`: audience and expiration propagation, mint-once-then-reuse, refresh past the margin, re-mint when the granted lifetime sits inside the margin, and failure wrapping as `ErrUnavailable` with the RBAC cause visible.
- Key-fetch transport: discovery and JWKS requests carry the projected token read from the mounted file, the file is re-read on every fetch so kubelet rotation is followed without restart, the env override replaces the file for host-process runs, and a missing or empty credential fails the fetch closed with a directed error.
- Middleware: 401/403/503 mapping, subject propagation, exempt-path passthrough (`/livez`, `/readyz`, `/metrics`, heartbeat), and enforcement on every other API path.
- Wiring: `FastletClient` attaches the header to every call and fails closed when minting fails without sending a request; `FastletServer.Handler` enforces authentication end to end and keeps the heartbeat open; the Pool Controller injects the anchor env into the Fastlet container, provisions the `fast-sandbox-fastlet` ServiceAccount before Pod creation, mounts exactly one projected token volume — the dedicated discovery-only identity's — into the Fastlet container and no other container, and strips template-supplied service-account and auth-token fields.
- Client error handling: plain-text 401/403/503 bodies surface the HTTP status instead of a JSON decode error; the middleware's machine-readable error envelope is decoded and classified as an authentication outcome that stays distinct from runtime `UnknownOutcome`, and a rejected Create carries a disposition proving the call never reached admission.

Acceptance criteria for the repository toolchain: `make test SCOPE=unit` passes on Linux for all affected packages (`internal/fastletauth/...`, `internal/protocol/fastlet`, `internal/fastlet/server`, `internal/controlplane/reconciler`, `internal/controlplane/{fastpath,orchestrator,fastletcontrol}`); the pre-existing darwin-only failures in `cmd/fsb-vm`, `cmd/sandboxtemplate-builder`, `internal/dataplane/fastletproxy`, `internal/fastlet/{infra,sandbox}`, and `internal/runtime/firecracker**` are unchanged.

Integration validation in the Firecracker integration environment: with everything in-cluster and the updated RBAC applied, `fastctl` Sandbox create, pause/resume, snapshot, and pool scaling work unchanged; `curl http://127.0.0.1:5758/api/v2/fastlet/create` without a token returns 401 while `curl .../api/v2/fastlet/heartbeat` returns 200; deleting the `serviceaccounts/token` grant produces Fast-Path errors naming the missing permission rather than traffic to Fastlets; restarting a Fast-Path Pod re-mints tokens and traffic continues without manual action.

Production pre-flight, in order: the cluster is v1.22 or newer; an admin mints an audience-bound token and decodes the `aud`/`exp` claims; `kubectl auth can-i create serviceaccounts/token` answers yes for both platform identities inside the control-plane namespace; and an **authenticated** GET of `https://kubernetes.default.svc/.well-known/openid-configuration` (and the JWKS URI it names) using the `fast-sandbox-fastlet` identity's projected token returns 200 — 403 means the authenticated issuer-discovery binding from `base.yaml` has not been applied, and rollout must stop there. An anonymous GET is expected to fail and its status is no longer meaningful.

## Rollout and rollback

The feature is always on; rollout is an ordered upgrade, not a staged flag flip. Deploy the RBAC change (the authenticated discovery pair replaces the anonymous binding), then the control-plane Deployments (which begin minting tokens and resolving the anchor), then Fastlet Pools, whose Pod templates pick up the injected anchor and the key-fetch token mount and roll through the normal Pool lifecycle. The anonymous binding and the token mount land in the same release, so an install is never in the state where Fastlets hold no credential and the cluster no longer grants anonymous reads. Signals to watch: the `Fastlet control authentication enabled` log on every control-plane Pod and Fastlet; Fastlet-side 401/403 counts surfaced through the existing HTTP status instrumentation; control-plane errors whose cause chain contains the TokenRequest failure. A missing RBAC grant or an absent anchor produces explicit errors, never silent fallback.

Rollback reverts images in the reverse order — Fastlet Pools first, then the control plane — because a new Fastlet rejects the unauthenticated old control plane while an old Fastlet merely ignores the header. There is no rollback to "this version with authentication off"; the only unauthenticated state is the previous version pair, which is the status quo this proposal replaces. No persisted resources, snapshots, or CRD objects are affected by rollback; the transient cost on either transition is the standard Fastlet Pod replacement effect on live Sandboxes.
