# Resource-Aware Per-Sandbox Overcommit

> Tracking issue: [#115 — Guide placement with CPU and memory budgets and pressure, not only slots](https://github.com/opensandbox-group/fast-sandbox/issues/115)
>
> Status: implemented behind independent controller feature switches
>
> Last updated: 2026-10-22

## Summary

`LegacySlot` answers one question: how many more Sandboxes may this Fastlet
manage? It does not describe the CPU and memory demand of each Sandbox. That
becomes inaccurate when one Pool accepts heterogeneous Sandbox sizes or when
memory pressure makes a nominally free slot unsafe.

`ResourceAware` keeps the slot boundary and adds a CPU/memory commitment
ledger. A caller specifies only the desired per-Sandbox runtime limits. The
Pool owns separate CPU and memory overcommit ratios, from which Fast Sandbox
derives requests:

```text
sandboxRequest.cpu    = ceil(sandboxLimit.cpu    / poolOvercommitRatio.cpu)
sandboxRequest.memory = ceil(sandboxLimit.memory / poolOvercommitRatio.memory)
```

The request is the admission charge. The limit is the runtime boundary. The
Fastlet admits a Sandbox only when both the slot ledger and the resource
ledger have room, and memory safety gates may still reject admission under
live pressure.

The complete control loop is:

1. FastPath resolves caller limits or Pool defaults.
2. FastPath derives the request from the immutable Pool policy.
3. Placement filters and ranks Fastlets using their aggregate ledgers.
4. Fastlet validates the derivation and atomically reserves the exact request.
5. The Create response immediately returns the new aggregate ledger snapshot.
6. Heartbeats remain the anti-entropy path for idle Fastlets, pressure changes,
   restarts, and lost responses.
7. The Pool scaler compares pending request vectors with effective free
   request capacity and adds Fastlet Pods when the buffer is short.

Fastlet remains the correctness boundary. Central state is an
eventually-consistent scheduling view, not a distributed reservation system.

## Problem statement

### Why slots are insufficient

A slot is a hard Sandbox-count boundary. It protects netns entries, runtime
state, file descriptors, and control-plane state, but it has no stable CPU or
memory meaning.

For example, three free slots do not say whether a Fastlet can accept:

- three Sandboxes limited to `250m / 512Mi`;
- one Sandbox limited to `4 CPU / 10Gi`;
- any new Sandbox while the parent cgroup is above its memory high watermark.

The original slot-only model can therefore select a Fastlet that has a free
slot but insufficient commitment capacity, or keep the Pool size unchanged
while all existing Fastlets are pressure-blocked.

### Why the Pool cannot have two capacity sources

The previous ResourceAware draft allowed both:

```text
sandboxResources.requests/limits * maxSandboxesPerPod
fastletTemplate.spec.containers[0].resources.requests/limits
```

These sources can disagree. A Pool may advertise ten Sandboxes while the
explicit Fastlet request contains only three commitments, or it may request
extra aggregate resources that the slot count can never consume.

ResourceAware therefore has one directional derivation. The runtime-owner
CPU and memory resources are generated by the Controller and cannot be
overridden in the first `fastletTemplate` container. Sidecars retain their
own Kubernetes resources and do not enter the Sandbox commitment formula.

## Goals

- Accept different CPU and memory limits for Sandboxes in the same Pool.
- Keep `maxSandboxesPerPod` as an independent hard count limit.
- Let callers express limits only; derive requests from Pool policy.
- Maintain one exact per-Fastlet commitment ledger.
- Make FastPath placement and Pool scaling consume the same ledger snapshot.
- React to live memory pressure without treating CPU and memory as identical.
- Reduce the 20-second heartbeat lag on active Create paths.
- Spread concurrent FastPath replicas without introducing node ownership.
- Preserve all existing `LegacySlot` behavior.

## Non-goals

- Dynamically changing overcommit ratios from observed usage.
- Treating observed RSS or CPU utilization as the commitment charge.
- Reclaiming, pausing, migrating, or evicting existing Sandboxes.
- Using swap as allocatable commitment capacity.
- Adding `maxSandboxLimits` or one shared `overcommitRatio`.
- Adding fixed Fastlet overhead or per-Sandbox overhead to this model.
- Building a central transactional reservation database.
- Replacing Kubernetes scheduling or node autoscaling.

## Public API

### SandboxPool policy and defaults

The existing flat `cpu`, `memory`, and `pids` fields remain compatible. In
ResourceAware mode, flat CPU and memory are the default per-Sandbox limits.

```yaml
apiVersion: sandbox.fast.io/v1alpha2
kind: SandboxPool
metadata:
  name: resource-aware
spec:
  maxSandboxesPerPod: 10
  capacity:
    poolMin: 1
    poolMax: 10
    bufferMin: 2
    bufferMax: 4

  sandboxResources:
    mode: ResourceAware
    cpu: "2"
    memory: 5Gi
    pids: 256
    overcommitRatio:
      cpu: "8"
      memory: "1.25"

  fastletTemplate:
    spec:
      containers:
        - name: fastlet
          image: fast-sandbox/fastlet:dev
```

The default Sandbox has:

```text
limit   = 2 CPU, 5 GiB
request = 250m, 4 GiB
```

CPU and memory ratios are independent. A shared ratio is intentionally not
part of the API.

### Per-Sandbox desired limits

FastPath Create accepts optional limits:

```yaml
resources:
  limits:
    cpu: "1"
    memory: 2500Mi
```

The Sandbox CRD stores the same caller-owned desired state:

```yaml
spec:
  poolRef: resource-aware
  image: alpine:latest
  resources:
    limits:
      cpu: "1"
      memory: 2500Mi
```

If `spec.resources` is omitted, the Pool flat CPU and memory values are used.
CPU and memory must be supplied together. Per-Sandbox resources are rejected
for `LegacySlot` Pools.

Only limits are public input. Requests remain derived state because allowing
callers to provide both would create another policy source and permit callers
to choose their own overcommit.

### Diagnostic annotations

FastPath and the standalone Sandbox Controller persist the derivation used by
the accepted assignment:

```yaml
metadata:
  annotations:
    fast-sandbox.io/resource-policy-hash: "..."
    fast-sandbox.io/resolved-request-cpu: 125m
    fast-sandbox.io/resolved-request-memory: 2Gi
    fast-sandbox.io/resolved-limit-cpu: "1"
    fast-sandbox.io/resolved-limit-memory: 2500Mi
```

These annotations explain the decision; they are not writable capacity
inputs. The Fastlet always validates the request again against its immutable
resource profile. They also fence direct CRD edits after the first assignment:
changing a per-Sandbox resource intent requires creating a new Sandbox.

### FastPath discovery

`PoolInfo.sandbox_resource_profile` exposes:

- mode;
- the default derived request;
- the default limit;
- PIDs;
- separate CPU and memory overcommit ratios.

`SandboxInfo.resources` exposes the caller-specified limits when present.

## Derivation and validation

### Request rounding

CPU division uses exact rational arithmetic and rounds up to a millicore.
Memory division rounds up to a byte. A derived request is never rounded down.

The ratios must be at least `1`. Limits must be positive, and CPU must be at
least `10m`, which is the minimum supported by the Linux CFS enforcement path.

### Default commitment capacity

The Controller derives the Fastlet's commitment budget from the Pool default:

```text
defaultRequest.cpu
  = ceil(sandboxResources.cpu / overcommitRatio.cpu)

defaultRequest.memory
  = ceil(sandboxResources.memory / overcommitRatio.memory)

commitmentCapacity.cpu
  = defaultRequest.cpu * maxSandboxesPerPod

commitmentCapacity.memory
  = defaultRequest.memory * maxSandboxesPerPod
```

`commitmentCapacity` contains only Sandbox budget. No fixed overhead is added.

### Runtime-owner envelope

The first Fastlet container owns the child cgroups or VMs. Its Kubernetes
request and limit are derived as:

```text
runtimeEnvelope.cpu
  = max(commitmentCapacity.cpu, defaultSandboxLimit.cpu)

runtimeEnvelope.memory
  = max(commitmentCapacity.memory, defaultSandboxLimit.memory)

runtimeOwner.requests = runtimeEnvelope
runtimeOwner.limits   = runtimeEnvelope
```

The `max` guarantees that the parent can contain at least one legal default
Sandbox limit even when a high overcommit ratio makes total commitment lower.

A caller-specific limit must not exceed this already-created envelope. Fast
Sandbox rejects an oversized Create request; there is no second maximum-limit
field.

### ResourceAware template validation

In ResourceAware mode, the first `fastletTemplate` container must not set CPU
or memory requests or limits. The Controller owns those four values.

Other Pod template fields remain user-owned, including image, environment,
scheduling constraints, security context, volumes, and sidecars. Sidecar
resources remain ordinary Kubernetes resources.

## Internal Create contract

The public desired object and resolved runtime configuration are separate:

```go
type SandboxDesiredSpec struct {
    Image        string
    Command      []string
    Args         []string
    Env          map[string]string
    WorkingDir   string
    Restore      *RestoreSpec
}

type RuntimeSandboxConfig struct {
    Identity SandboxIdentity
    Desired  SandboxDesiredSpec
    Limits   SandboxRuntimeLimits
}
```

The FastPath-to-Fastlet Create request additionally carries the resolved
admission contract:

```json
{
  "resources": {
    "requests": {"cpu": "125m", "memory": "2Gi"},
    "limits": {"cpu": "1", "memory": "2500Mi", "pids": 256}
  }
}
```

Fastlet verifies the resource profile hash, limit validity, request derivation,
PIDs, runtime envelope, static capacity, and dynamic admission state before
creating runtime side effects.

After admission, RuntimeDriver receives only `RuntimeSandboxConfig` with
resolved limits. Requests are not runtime QoS settings in this phase; they do
not configure CPU weight, `memory.low`, priority, or per-Sandbox QoS.

## Fastlet commitment ledger

### Exact heterogeneous accounting

Fastlet stores each accepted Sandbox's resolved limits in durable runtime
metadata. It recomputes that Sandbox's request from the immutable Pool ratio
when constructing the aggregate ledger.

```text
committed.cpu    = sum(derived request CPU of each live reservation)
committed.memory = sum(derived request memory of each live reservation)
```

The ledger does not multiply the number of active Sandboxes by a default
request. This is essential once Sandboxes have different sizes.

### Lifecycle accounting

A commitment is acquired before runtime side effects and is retained while a
Sandbox is Creating, Running, Pausing, or Resuming. It is released only when
runtime absence is proven after successful delete, completed pause, failed
create cleanup, or startup recovery.

An accepted Creating or Resuming Sandbox is already included in the Fastlet
ledger and must not also be counted as central pending demand.

### Atomic admission

Under one Fastlet lock, Create checks:

```text
activeSandboxes + 1 <= maxSandboxesPerPod
committed.cpu + candidate.request.cpu <= capacity.cpu
committed.memory + candidate.request.memory <= capacity.memory
dynamicAdmissionState in {OPEN, DEGRADED}
```

Only then is a placeholder reservation inserted. Runtime creation happens
after the reservation. Duplicate Create requests reuse or fence the existing
identity instead of charging twice.

## Aggregate snapshots and freshness

### Snapshot schema

Fastlet publishes aggregate resource admission state:

```json
{
  "version": "v2",
  "epoch": "fastlet-start-uuid",
  "revision": 42,
  "capacity": {"cpu": "2500m", "memory": "40Gi"},
  "committed": {"cpu": "625m", "memory": "10Gi"},
  "state": "OPEN",
  "reason": "NONE"
}
```

Per-Sandbox reservations remain Fastlet-local. Central components consume the
aggregate capacity and committed vectors.

`epoch` changes after Fastlet restart. `revision` increases when commitments
or admission state change. Central state accepts a newer epoch or a
non-decreasing revision and rejects older feedback.

### Request piggyback and heartbeat

Successful Create, definitive Create rejection, and Delete responses carry
the full aggregate admission snapshot. FastPath or the Controller applies it
immediately to the same registry used for placement. Delete is asynchronous,
so the first response may still include the terminating reservation; a later
delete poll reports the released ledger as soon as runtime absence is known.
This removes the heartbeat-period delay on the hottest mutation paths.

Heartbeat remains mandatory. It repairs lost responses, reports idle
Fastlets, refreshes staleness, propagates background memory pressure, and
reconstructs state after process restart. Piggyback is an optimization, not a
new authority.

ResourceAware placement fails closed when either the heartbeat or resource
snapshot is stale.

### Local in-flight reservations

Each FastPath replica temporarily reserves the selected slot and request in
its own registry while Create is in flight. This prevents concurrent requests
handled by one replica from all consuming the same stale free capacity.

The reservation is released when the RPC returns. A returned Fastlet snapshot
then supplies the authoritative committed value. Reservations are deliberately
not distributed across FastPath replicas; cross-replica races are resolved by
Fastlet atomic admission.

Create feedback also publishes the accepted Sandbox identity into the local
registry. An idempotent retry for the same instance generation and assignment
attempt therefore does not reserve the same request a second time.

## FastPath placement

### Hard filters

ResourceAware placement requires matching revisions, readiness, no drain,
fresh heartbeat and resource state, an eligible admission state, a free slot,
and enough CPU and memory commitment after local in-flight reservations.

`BLOCKED`, `UNKNOWN`, and stale states are ineligible. Fresh node-scoped memory
pressure also blocks other Fastlets observed on the same node.

### Ranking and FastPath seed

Eligible candidates are ordered by:

1. admission state (`OPEN` before `DEGRADED`);
2. image cache hit;
3. coarse dominant-load bucket;
4. FastPath replica preference;
5. Sandbox-stable tie-breaker.

The FastPath Deployment injects its Pod UID as `POD_UID`. The registry uses
`hash(POD_UID, fastletID)` inside a 10-percent dominant-load bucket. Different
replicas therefore have visibly different preferences across otherwise
equivalent Fastlets. The seed changes ranking, not ownership, and never
overrides readiness, pressure, capacity, or a different load bucket.

## CPU and memory policy

CPU and memory both participate in static commitment admission, but their
operational behavior is intentionally asymmetric.

CPU is compressible. Overcommit usually causes contention, throttling, and
higher latency rather than immediate failure:

```text
CPU overcommit ratio = limit.cpu / request.cpu
```

Phase one performs static CPU commitment checks only. High observed CPU usage
does not dynamically block admission.

Memory is not safely compressible in the same way. Pressure can cause reclaim,
severe latency, or OOM termination:

```text
Memory overcommit ratio = limit.memory / request.memory
```

In addition to static commitment, the Fastlet observer may block new creates
from parent-cgroup watermarks, memory PSI, cgroup OOM events, Kubernetes node
memory pressure, or stale telemetry.

Dynamic memory admission only blocks new Sandbox creation. It does not pause,
migrate, reclaim, or evict existing Sandboxes.

## Pool elasticity

### Effective free capacity

For each fresh, open Fastlet and candidate/default request:

```text
slotFree   = slots.capacity - slots.used - localInFlightSlots
cpuFree    = floor((capacity.cpu - committed.cpu - inFlight.cpu) / request.cpu)
memoryFree = floor((capacity.memory - committed.memory - inFlight.memory) / request.memory)

effectiveFree = min(slotFree, cpuFree, memoryFree)
```

Blocked, stale, unknown, and draining Fastlets contribute zero schedulable
free capacity.

### Pending demand and scale-up

The scaler sums the exact derived request of each pending Sandbox. Accepted
Creating and accepted Resuming Sandboxes are excluded because their requests
already appear in `committed`.

The Pool scales up when free Sandbox count, free CPU commitment, or free memory
commitment falls below pending demand plus `bufferMin`. The number of added
Pods is the maximum deficit across the three dimensions, bounded by `poolMax`.

A newly created Fastlet contributes nominal capacity only during a bounded
startup grace period. A Pod that never reports a heartbeat stops masking
replacement demand after that grace period.

### Scale-down and drain

Scale-down considers empty Fastlets only. After capacity remains above
`bufferMax` for the stabilization window, the Controller marks exact drain
candidates and removes them after drain acknowledgment.

The stabilization timestamp is represented by the
`ScaleDownCandidate=True` Condition's `lastTransitionTime`; no separate status
timestamp field exists.

If a scale-down candidate becomes loaded before completion, the Controller
cancels that drain after the timeout. It does not force-delete a loaded
Fastlet. TTL may become a future candidate-ranking hint, but ordinary
scale-down does not depend on predicted Sandbox expiry.

## Pool status

Legacy top-level counters remain for compatibility. New summaries are grouped
by the view an operator needs:

```yaml
status:
  currentPods: 4
  readyPods: 4
  idleFastlets: 1
  busyFastlets: 3

  fastlets:
    desired: 3
    current: 4
    ready: 4
    idle: 1
    busy: 3
    draining: 1

  resources:
    capacity: {cpu: "10", memory: 160Gi}
    committed: {cpu: "6.5", memory: 104Gi}
    free: {cpu: "2", memory: 32Gi}

  sandboxes:
    total: 26
    assigned: 24
    pending: 2
    running: 20
    paused: 2
    terminating: 1
    failed: 1

  summaryObservedAt: "2026-10-22T08:00:00Z"
```

Resource values are request-based commitment values after overcommit, not
physical node usage. `capacity` is aggregate commitment capacity, `committed`
is accepted Sandbox requests, and `free` is currently schedulable commitment.

The structured summary is an observability projection, not the live placement
ledger. It is rate-limited to approximately one minute to avoid frequent CRD
status writes.

## Compatibility

A mode-less existing profile remains LegacySlot:

```yaml
sandboxResources:
  cpu: "1"
  memory: 1Gi
  pids: 256
```

LegacySlot preserves the old flat resource API, slot-only admission and
placement, `maxSandboxesPerPod`, explicit first-container aggregate resources,
and existing aggregate overcommit behavior. It does not invent a per-Sandbox
request or accept per-Sandbox limit overrides.

Static Fastlet admission, dynamic memory admission, ResourceAware placement,
and ResourceAware Pool scaling remain independently disableable. This permits
shadow telemetry and staged rollback without replacing the immutable Pool.

## Failure semantics

- A definitive pre-side-effect Fastlet rejection may advance to another
  candidate.
- An ambiguous Create outcome retains the durable assignment and is retried
  idempotently; it is never double-scheduled immediately.
- Older heartbeat revisions cannot clear newer rejection feedback.
- A restarted Fastlet uses a new epoch and reconstructs commitments from
  durable runtime state.
- Stale or malformed resource snapshots fail closed for ResourceAware
  placement.
- `poolMax` may prevent replacement capacity; the Pool exposes the shortage
  rather than violating admission.

## Worked example

Pool defaults:

```text
maxSandboxesPerPod = 10
default limit      = 2 CPU, 5 GiB
ratio              = 8 CPU, 1.25 memory
default request    = 250m, 4 GiB
```

Derived Fastlet contract:

```text
commitmentCapacity = 2.5 CPU, 40 GiB
runtimeEnvelope    = max(capacity, default limit)
                   = 2.5 CPU, 40 GiB
```

A caller requests a smaller Sandbox:

```text
limit   = 1 CPU, 2.5 GiB
request = 125m, 2 GiB
```

If the Fastlet already committed `2 CPU / 36 GiB`, the new Sandbox passes
static admission, leaving `375m / 2 GiB`. If the Fastlet is memory-pressure
blocked, the same Sandbox is rejected despite static room, and the Pool treats
that Fastlet as contributing zero schedulable free capacity.

## Validation requirements

The implementation is covered at four levels:

- unit tests for ratio validation, exact rounding, and envelope derivation;
- Fastlet tests for heterogeneous commitments, atomic concurrency, pressure,
  restart recovery, and release;
- placement and Controller tests for freshness, feedback ordering, local
  reservations, seeded ranking, pending vectors, status summaries, startup
  grace, stabilization, and drain cancellation;
- Linux/Kubernetes E2E for per-Sandbox limits, scale-out, pressure blocking,
  and scale-down.

## Rejected alternatives

- **Public requests and limits:** lets each caller choose its own overcommit
  and creates two policy authorities.
- **Fastlet template as capacity input:** produces conflicting aggregate
  capacity and cannot explain which value wins.
- **One shared ratio:** hides the different CPU and memory risk policies.
- **Observed usage as request:** makes admission unstable and unsafe.
- **Distributed central reservations:** adds consensus-level complexity while
  Fastlet must still remain authoritative.
- **Pure heartbeat synchronization:** leaves an avoidable delay after active
  Create mutations.
- **Streaming connections from every Fastlet:** may reduce latency further but
  adds connection lifecycle, backpressure, routing, and rollout complexity;
  response piggyback plus heartbeat is the lower-cost step.
- **Forced loaded scale-down:** risks terminating active Sandboxes for ordinary
  elasticity.
